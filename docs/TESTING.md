# What has been tested

Italian version: [PROVE.md](PROVE.md).

Test record for version 0.1.0 (25 October 2026). "Executed" means run and observed, not inferred
from reading the code. *(review)* marks findings from our own adversarial reviews.

## Executed

### Automated tests and CI

- **442 automated tests** pass on macOS (Python 3.14) and in CI on every change (Linux with Python 3.9, 3.11, 3.13, Windows, macOS). The 399 of the 0.1.0 package also ran unzipped on Linux (Python 3.9 and 3.13). Server (board, sto bene (I'm safe), notices, CAP, PFIF, codes, limits, Range, path traversal, captive portal, connection cap, local-only admin, full disk, network errors, smuggled requests, internet names), search and hostile maps, navigator, USB copy and prepared sticks, sharing, launchers, signed notices, signed versions, updating from a stick, one password per person, nginx, setup, languages, Windows firewall.
- **They catch broken defenses**: 3 planted faults (no path containment, Range ignored, any code accepted) make them fail.
- **Windows 11 ARM64** (Python 3.13): 291 green before the navigator review fixes, 48 skipped (Mac and Linux only). CI runs all of them on GitHub's Windows runner, firewall attack and planted `py.bat` included.
- **shellcheck** (7 scripts, Debian Trixie) and **ruff**: clean.
- **Bandit, Semgrep** (48 files) and a DOM sink search (`innerHTML`, `eval`...): nothing. Bandit's hits are intentional (processes started with an argument list, listening on all interfaces on the laptop). Both tools first caught bugs planted in a decoy file.

### Security and attacks

- **Malicious text on the board** (`<img src=x onerror=...>`): shown as plain text, never run.
- **Slowloris** (260 drip-feed connections from one device): blocked everyone for the whole attack. Fixed: another device now works normally.
- **Review as an attacker**: duplicate JSON keys, invisible characters, nested JSON, timer cost, nginx logs, Wikipedia's origin, hotspot services. 6 fixes. The per-request timer cost 27% of performance and became one watchdog (performance back, and without it the 3 timeout tests fail).
- **Board flooding**: per-device limits by MAC, an emergency brake that holds new posts, approve or close in batches from the admin page. A phone with two IPs counts as one, also through nginx and the systemd sandbox. No MAC or IP is stored. Removing any defense fails the tests.
- **Network fuzzing** (no network): 250,000 requests mutated from valid ones (types, huge numbers, NaN, hostile Unicode, nesting, headers, Range, absurd lengths and methods), as phones and from the Campanile itself. Two HTTP 500s fixed (a lone surrogate in a password or a signed notice). Then 200,000 more: no 500s, no stack traces, server up, database intact. The fuzzer first found a planted defect.
- **Our signature check** (`campanile/ed25519.py`, for laptops without `cryptography`): the RFC 8032 vectors and Google's 210 Wycheproof cases, with OpenSSL's answer on every one of them and on 12,000 random and damaged signatures. Without the check that refuses a signature written another way, the tests fail. Every signed-notice test runs twice, with OpenSSL and with ours.
- **Signed versions** (`campanile/release.py`, `scripts/sign-release.py`): a signed folder passes; one changed, added or missing file is refused (an added `campanile/secrets.py` too, which would run before our code), as are an unknown key, a changed signature or version, an older or equal version, and a notice's signature passed off as a release's. Keys made with a passphrase and file mode 600, a wrong passphrase refused, signing refused for a key Campanile doesn't know. A checker that ignored added files makes the tests fail. On Python 3.9 and 3.13.
- **Updating from a stick** (`campanile/update.py`): a newer signed version is copied next to the Campanile and checked there; an unsigned, changed or older one is refused and nothing stays. A stick changed after the check changes nothing; a prepared copy changed before the restart is thrown away and the old version starts. Data and tools move into the new folder, journal style: stopped at any of the five steps, as a power cut would, it is finished at the next start, a locked file stops everything until the next start, and a Campanile never starts empty while its data sits elsewhere (new folder deleted, or data in both: it stops and says where). The setup page job, the hand-over at start and the Raspberry path (signed installer run with the saved choices; an unsigned stick installs nothing). Taking out the second check, the stop after the point of no return or the never-start-empty rule makes the tests fail.
- **The 0.1.0 package, before signing**: built from a fresh clone on a Mac and in Linux, its 1,147 signed files identical. All 399 tests on the unzipped package (macOS with Python 3.14, Linux with 3.9 and 3.13). Started like a user would: 11 pages of 11, a post, the admin page, a person added. Updated end to end to a test 0.1.1 on a Mac (setup page, FAT32 stick) and on Windows 11 ARM (real double click): posts, password and people carried over; a stick changed on purpose refused.

Downloaded from Releases like anyone would: the SHA-256 matches, our checker says "Signed by CarrotStudio: Campanile 0.1.0", `gh attestation verify` passes, and the same zip with one file changed fails.
- **The computer's language** (29 October 2026): the laptop's window, the Raspberry's update and the launchers' last line follow the computer's settings, Italian or English. On a clean Windows 11 ARM in Italian, with Python 3.14.9 from python.org (signature valid): Campanile read `it_IT` with no environment variables, the real double click opened the window in Italian, and closing left no process. All 412 tests there: one of ours assumed it wasn't on Windows; fixed. A test fails if the language stops coming from Windows' settings.

### Load, endurance and failures

- **Load, laptop mode** (Linux container, 2 CPUs): simulated phones that act like browsers (4 open connections, an update every 30 s, map, submissions), each with its own address. 300 in one minute: all in, no errors. **300 in 5 s: only 64 got in**, the slots full of idle connections. Fixed by freeing the longest-waiting slots and turning off Nagle's algorithm (40 ms on every response): **300 of 300**, home in at most 0.05 s. 600 in 5 s: 599 of 600, home 10 s median. Neither fix works alone (measured), and without the first the new test fails.
- **Load, Raspberry setup** (Debian 13 container, 2 CPUs, real `install.sh`, nginx, systemd): 100 in 30 s, 300 in 5 s, 600 in 5 s, 1,000 in 10 s, **all in, no errors**. Fixed a ~40 ms delay on every map tile (Debian's `tcp_nopush` with the phone's delayed ACK): 95th percentile 48 → 0.5 ms, control with `sendfile off`. nginx check after: 47 of 47. This CPU is faster than a Raspberry's, so real timings must be measured in the field.
- **Raspberry with few resources** (Docker, Debian 13, 512 MB RAM, no swap, capped CPU, real `install.sh` with nginx, medical Wikipedia and a map, phones from a second container, each with its own IP):
  - 1 core: 300 phones in 5 s and 1,000 in 10 s, **all in, 0 errors**. Home 0.01 s at the 95th percentile, at most 41 MB of RAM (Campanile 18, Kiwix 5, nginx 3), CPU 10%.
  - **A tenth of a core**, about a Raspberry Pi Zero 2 W (estimated from the measured cost per request on one Mac core: API 140-190 µs, nginx 18-41 µs): 1,000 in 10 s, still 0 errors, updates 40 ms at the 95th percentile.
  - **Breaking point**, a twentieth of a core: the API slows into timeouts, connections pile up, nginx runs out of its 768 slots per process (Debian's value). 115 of 1,000 phones miss the home page with nginx 500s. Static pages still load (95th percentile 62 ms).
  - Wikipedia: 300 phones in 10 s, 3 articles each (900 pages, 157 MB), 0 errors, 95th percentile 4 ms even at a tenth of a core. Kiwix: 0.4 ms of CPU per article, 33 MB of RAM.
  - In the field the limit will be Wi-Fi bandwidth, not the CPU. Bench limits: a capped CPU is not a slower one, and the simulated phones share one MAC.
- **Load and endurance on Windows 11 ARM64**, where the code that closes connections differs (phones simulated inside the machine, each with its own address): 300 phones in 5 s all in, home in at most 0.03 s. 150 phones for 10 minutes: memory flat at 34-36 MB, handles and threads stable and back to start, no stack traces. The generator first counted server-closed updates as errors (Windows names that error differently). Fixed: 0 errors in 1,354 updates. Control, real Chrome for 155 s: 12 of 12 requests, no stale warning.
- **30-minute endurance** (Linux container, 150 phones, sampled every minute): 20,427 requests, no errors. Memory flat at ~42 MB, threads and open files steady (~55, ~60), back to 2 and 7 when the phones left. No leaks.
- **`kill -9` mid-write**, 30 times, with 8 writers publishing posts and names from different addresses: 104,481 writes tried, 6,398 confirmed, **none lost**, database intact every time. The checker first caught a confirmed post deleted on purpose. A killed process is not a power cut (the OS cache survives): that needs a real Raspberry.
- **Wrong clock** (a Raspberry has no clock battery and, offline, wakes at its switch-off time): Campanile 3 days behind (`faketime`), Chrome on time. A fresh post looked 3 days old. Now times follow the phone's clock (offset from the `Date` header, ignored under 2 minutes) and signed notices say until when they're valid. Old code: 19/10 instead of 22/10.
- **Full disk** (4 MB, filled to the last byte): home, notices and board stay readable. Submissions get a clear message instead of "errore interno" (internal error). With space freed it works again, database intact.
- **`kiwix-serve` is never orphaned**: it stops within 2-3 s after Ctrl+C, closing the window (SIGHUP), SIGTERM, even `kill -9` of Campanile.

  - «Prepare for every computer» fetches Kiwix for 5 systems and Python 3.14.9, checking python.org's Sigstore signature (a tampered file and a wrong identity are refused). The stick appears by itself, «Copied» in 6 s: 897 files, **0 hash mismatches, no private data**.
